### Criterion 3 — a note on scope

Criterion 3 holds exactly for secrets of role `.credential` — there the
secret sits in the grouping key, so all group members carry the same
value, and "deleted" never means loss. For `.passphrase` it does NOT hold
literally: those members may carry different stored passphrases (the
passphrase is deliberately not in the key), and `applyMerge` copies the
first one found onto the set and deletes the rest
(`SessionListViewModel.swift:634-642`). That is defensible on its merits —
the same key file has one passphrase — and **pre-existing since M10b, not
introduced by M24**. The verdict "met" stands unchanged; only the scope of
the wording is clarified here.

### Criterion 4 — the permitted changes, and the one borderline one

The spec permitted exclusively re-reading a claim onto its new seat with
the same claimed value. Task 2 made five such re-reads
(`candidate.username` → `displayLabel`, `candidate.authKind` →
`values[SSHField.authKind]`, `candidate.keyPath` → `values[SSHField.keyPath]`)
and **a sixth that the implementer themselves flagged as borderline**:

```
candidate.keyPath == nil   →   candidate.values[SSHField.keyPath] == ""
```

The literal value had to change because `FieldValues.subscript` never
returns an Optional (`storage[key] ?? ""`, `BackendFieldID.swift:57-60`) —
`== nil` would not even type-check. The semantic claim ("no key path was
carried for an agent login") is unchanged. This is the only adjustment
outside the letter of the spec.

**No SSH test changed its inputs, its `sessionIDs` result, or its
candidate count** — the boundary whose violation the spec would have
counted as a finding. A rework that would have shifted SSH behaviour is
therefore not present.

As a counter-check on criteria 4/5, the close-out additionally **swapped
the `SecretRole` declaration on a trial basis**
(`SSHField.password` → `.passphrase`, `SSHField.passphrase` →
`.credential`) and ran `swift test --filter LoginMergePlanner`: **5 tests
turned red**, among them `privateKeySessionsGroupWithoutReadingTheKeychain`,
`groupsByUsernameAndKeyPath`, `groupsByUsernameAndPasswordValue`,
`newMemberReactivates` and `sessionWithoutStoredPasswordExcluded`. This
answers the doubt deferred from Task 1 ("the guards only pin the
**presence** of `secretRole`, not the **value**"): the values are pinned
behaviourally. The change was reverted afterward.

## For the release notes

The three points from the spec, plus three that came up during
implementation:

1. **Merge suggestions now also exist for S3 and WebDAV** — and they
   produce a set of the correct protocol. Previously the suggestion for
   these protocols was faulty and, on acceptance, deleted the stored
   credentials.
2. **Object-storage and WebDAV connections can no longer be selected as a
   jump host.** An existing configuration pointing at one now reports, in
   plain text, "Only SSH connections can be used as a jump host." when
   connecting, instead of producing a non-functional bastion.
3. **Deleting a non-SSH connection that a jump host refers to no longer
   copies anything back into the referencing connection.** It reports on
   the next connect that the referenced connection is missing.
4. **An anonymous WebDAV connection is never suggested as a merge
   candidate.** New: a visible secret field of role `.credential` with no
   stored secret excludes the session from grouping — the previous SSH
   rule, now for every protocol.
5. **A session whose protocol claims a configuration block it does not
   carry** (corrupted stored data) no longer appears in merge
   suggestions, instead of being grouped via the SSH fallback values of
   `""`/`.password`.
6. **The ordering of merge suggestions has changed:** instead of
   username → key path → group size, now display label → protocol →
   group size. Purely cosmetic, but visible when several suggestions are
   pending at once (see also the stability minor below).
7. **An unadvertised security improvement in export:**
   `SessionListViewModel.exportPayload` calls `LoginResolver.resolveJump`
   under `try?` to populate the export's `jumpPassword` field
   (`SessionListViewModel.swift:863-876`). Before Task 4, this returned
   NOT `nil` for a session whose jump pointed at an S3 session —
   `sshLogin` returns `nil` for a session-bound (not set-bound) S3
   reference, the fallback branch in `resolveJump` then unconditionally
   reads `secrets.password(for: referenced.id)`
   (`LoginResolver.swift:225-229`), and under exactly that keychain ID an
   S3 session stores its **secret access key** (the same slot that
   `exportPayload` elsewhere deliberately treats as `s3SecretAccessKey`,
   not as `password`). So the export wrote the secret access key into
   `jumpPassword` — a field that is interpreted as an SSH password on
   import. The new `.jumpSessionNotSSH` throw now lets `try?` return
   `nil`, which leaves `jumpPassword` simply empty: unlike its neighbour
   fields (`jumpHost`, `jumpPort` …), it has no `?? jump.X` fallback onto
   the jump spec, but becomes `nil` and counts in
   `missingPasswordCount`. Not required by the spec, but a fix worth
   having in the release notes.

### E. Follow-ups from the whole-branch review

These three did not come from any of the five task reviews, but from the
final review over `45ba1aa..HEAD`. None is Critical or Important; all
three are deliberately NOT fixed in this pass, so they survive the
git-ignored execution ledger:

- **`SessionListViewModel.delete`, lines 244–257: with `affected == []`,
  bastion resolution still runs into nothing.** `resolvedSSHLogin(for:
  session)` is called unconditionally, and if that returns `nil` and
  `session.authKind != .agent`, line 256 reads
  `secrets.password(for: session.id)` — for an `.s3` session that pulls
  its secret access key from the keychain, only to discard it afterward
  because the loop over `affected` (line 260) is empty for this case.
  An `if !affected.isEmpty { … }` around this block would avoid that and,
  in doing so, remove three of the five unprotected readers named in the
  criterion-4 section. **Recommended as the opening move of the next
  milestone, deliberately not implemented here.**
- **`LoginGroupKey.kind` is structurally redundant.** The field keys are
  namespaced (`ssh.*` vs. `s3.*` etc.), so two backends can never produce
  equal `fields` dictionaries — no test can distinguish the presence of
  `kind` in the key from its absence. The actual protection against mixed
  groups is `applyMerge`'s own guard
  (`groupSessions.allSatisfy({ $0.kind == candidate.kind })`,
  `SessionListViewModel.swift:621`), which is also tested
  (`applyMergeRefusesACandidateWhoseSessionsAreOfMixedKind`). The doc
  comment on `LoginGroupKey.kind` credits the field with work that the
  namespacing already does.
- **`applyMerge` checks `kind`, but not `hasStoredConfiguration`.** A
  hand-built `.s3` candidate over two blockless `.s3` sessions would
  produce a set with an empty `accessKeyID` and still delete both session
  slots. `LoginMergePlanner.candidates` already filters such sessions out
  (`guard descriptor.hasStoredConfiguration(session) else { continue }`,
  `LoginMergePlanner.swift:64`), so this path is unreachable via the
  planner — only via a hand-constructed candidate, which `applyMerge`'s
  own mixed-kind guard also addresses.

## What the process produced

**The plan's file lists were incomplete twice, and both times the
compiler found it, not the review.**

- Task 2: the list did not name `SessionListViewModel.applyMerge`, which
  read all three removed candidate properties. The implementer had to
  build a documented compatibility shim, which Task 3 then removed again
  — two rounds of work for zero behaviour change.
- Task 3: the list for the rename `suggestedSetName(forUsername:)` →
  `(forLabel:)` named only `LoginSetsSheet.swift`;
  `ConnectionFormView.swift:857` and `ContentView.swift:2280` also called
  it. A signature change without a complete call-site list is a
  guaranteed red build.

After the second incident, the briefs for Task 4 and 5 were amended with
the instruction to **grep the call sites themselves rather than trust the
list**. After that, the case did not recur; Task 5 found the
`SessionSidebar` finding (section A) this way on its own, which no file
list contained.

The generalized version, as an addendum to the M23 lesson ("a comment
that claims something about code needs the same verification as a test"):
**a plan's file list is a hypothesis, not an inventory. Whoever changes a
signature or a structure greps the call sites.**

Second, and applied in this very close-out: **where the question is
"which places does this affect?", the compiler is a better witness than a
grep.** The Step-4 grep from the brief would have delivered over 200
hits, most of them wrong; two compiler probes (deletion, then
`@available(*, deprecated)`) delivered the exact set of 17 + 38 sites in
one pass.

Third: the whole-branch review over `45ba1aa..HEAD` (mentioned in the
last section of this report as still pending) found two further
instances of the same class that the plan had not had on its radar — four
doc comments that carried forward the old enumeration of `resolveJump`'s
errors (`LoginResolver.swift`, `SessionListViewModel.swift`,
`ContentView.swift`, `ConnectionFormView.swift`), and
`SessionSidebar.deleteConfirmMessage` (section A), whose counter had no
`kind` filter even though Task 5 had introduced the exception case long
before. Three of the four doc comments (`LoginResolver.swift`,
`SessionListViewModel.swift`, `ContentView.swift`) named the old error
cases by name (`.missingJumpSession`, `.jumpChainNotSupported`) and would
have turned up with a grep on `LoginResolveError` or one of its case
names; the fourth (`ConnectionFormView.swift`, `eligibleJumpSessions`)
describes the eligibility filter in prose, without naming an error case,
and would not have been found that way — it would have needed a grep on
the changed function itself (`JumpSessionEligibility.eligible`). The
sharper rule drawn from the three: **whoever adds a case to an error
enum greps the enum's name (or its existing cases') in the prose, not
only its call sites** — that would have found three of the four findings
ahead of time. The fourth still needs the grep on the changed function
itself, which the M23 lesson already demands.
