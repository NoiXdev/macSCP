# M20 — CLI expansion: S3, transfers, shared keychain (design/spec)

**Date:** 2026-08-03
**Status:** approved (maintainer), ready for writing-plans
**Branch:** `develop`
**Occasion:** The parked roadmap item "macSCP CLI / open-with-S3 CLI". An
earlier brainstorming session on the topic is marked done on the task board,
but left neither a spec nor a plan; this restarts the content from scratch.

## Goal

`macscp-cli` moves from an M1 driver to a tool that uses the same stored
sessions as the app — for SSH **and** S3 — and that works both at the
terminal and, without prompts, in cron and CI.

## Starting point (verified in code)

`Sources/MacSCPCLI/MacSCPCLI.swift` is 51 lines from M1:

- **A single command:** list an SFTP directory. No transfer.
- **No S3.** The backend dispatcher from M12 (`BackendConnector`) bypassed
  the CLI; it builds its own `SSHConnectionConfig`.
- **No access to stored sessions.** Host, port and user come in as flags,
  the password from `MACSCP_PASSWORD`.
- **Auto-trust for host keys** (`MacSCPCLI.swift:28`): unknown keys
  are accepted automatically, the fingerprint only printed to stderr.

The last point contradicts the architecture invariant ("unknown keys require
explicit consent; there is no accept-anything path"). It disappears in this
milestone, **before** new commands are added — otherwise there would be a
window in which a more capable tool carries the old weakness.

Existing and reusable, on the other hand: `BackendConnector`,
`TransferEngine` (resume, throttling, conflict rules), `S3FileSystem`
(multipart, range GET), `SessionStore`, `LoginSetStore`, `LoginResolver`,
`KnownHostsStore`, `SecretStore`. The CLI rebuilds none of it.

## Maintainer decisions

| Question | Decision |
|---|---|
| Purpose | Both: terminal companion **and** automation, switched via `--non-interactive` or a missing TTY |
| Credentials | Share the keychain fully, with tiered resolution as a fallback path |
| Host keys | Ask interactively, otherwise abort; plus an explicit `--accept-new` |
| Tier 1 scope | `ls`, `get`, `put`, `rm`, `mkdir` — for SSH and S3 alike |
| Architecture | Decision logic moves to Core, CLI stays wiring |

## Architecture

### Why the logic moves to Core

The App target has no test target of its own (`Package.swift` declares only
`macSCPCoreTests`) — that is exactly why the icon guard from M19a had to
scan source instead of checking behavior. A CLI target without tests would
repeat the same mistake, this time on security-critical logic. Core has the
test infrastructure, and session resolution, secret retrieval and trust
decisions are Core concerns anyway: the App needs them too.

### New Core types

**`SessionReference`** — parses `prod:/var/www` into a name part and a
path and resolves the name against the `SessionStore`. The type must
handle: unambiguous name, ambiguous name (several sessions with the same
name), unknown name, paths that themselves contain colons, and the case
without a prefix (= local path). Resolution also works via the session
UUID, so scripts can run against a stable identifier instead of a
renamable name.

**`SecretResolver`** — the tiered resolution as its own type with
interchangeable sources. Reports, along with the secret, **which** source
delivered it (for `--verbose`).

**`HostKeyPolicy`** — the three states (ask / reject / `--accept-new`).
The decision is a pure function of policy, TTY availability and key
state, so every combination can be run through in tests.

**`TransferPlan`** — maps a source and destination spec onto concrete
jobs: file → file, file → directory, directory → directory (recursive).
Holds the conflict decision per job.

### One move within the existing codebase

`HostKeyDecider` currently sits on `ConnectionViewModel`, i.e. in the
presentation layer; `BackendConnector.connect(_:decider:)` requires it that
way. A CLI has no view model and would have to borrow a type from the UI
layer to build a connection. The type moves to `Connection/`, leaving a
`typealias` at the view model — no caller changes.

### What stays in the CLI

Command definitions (ArgumentParser), output formatting, TTY detection,
mapping errors to exit codes. No decision logic that isn't checked in Core.

## Login

### Order: explicit beats implicit

The SSH agent is **not** a secret source but an authentication method: with
`authKind = .agent`, no secret is needed at all. The chain applies only to
what a session actually needs (password, key passphrase, S3 key pair):

1. **`--password-command`** — always wins. The secret comes over stdout
   of the invoked command. There will **not** be a `--password` flag:
   it would show up in the process list.
2. **Environment variable** — the CI path. For S3, the usual
   `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, so existing pipelines
   don't have to relearn anything.
3. **Keychain** — the convenient default case at the workstation.

Empty returns count as "not delivered" and lead to the next source; a
source that aborts with an error (e.g. `--password-command` with a
non-zero exit code) aborts the whole attempt instead of silently sliding
on to the next one — otherwise a broken vault call would silently fall
back to an old keychain password.

### Sharing the keychain

A shared `keychain-access-group` needs a team ID prefix and entitlements
in **both** binaries, plus signing the CLI in the release script
(`scripts/release` today only signs the App).

**The group is attached optionally, not required.** The dev build is
ad-hoc signed (`TeamIdentifier=not set`) — if the group were mandatory,
development would be blocked and the path not even locally testable.
`SecretStore` keeps working without the group.

**Migration:** Existing entries carry no access group, because that is an
attribute set at creation time. Without migration, the CLI would fail to
see exactly the oldest sessions. The sequence is **write new → verify →
only then delete the old entry**. If it aborts midway, the secret exists
twice (unpleasant, but lossless); the reverse order would be data loss.
The migration is idempotent and may run any number of times.

## Host keys

- **Mismatch → always a hard abort**, no prompt, exit code 12. The
  decider is not consulted (invariant from M3c).
- **Unknown key, TTY present:** show the fingerprint, ask for
  confirmation.
- **Unknown key, no TTY or `--non-interactive`:** abort with
  exit code 11.
- **`--accept-new`:** enters only unknown keys. It changes nothing about
  mismatch behavior.

Exit codes 11 and 12 are deliberately different: "new host" is a work
item, "key has changed" is an alarm. A script that treats both the same
way throws away exactly the distinction TOFU exists for.

## Commands

```bash
macscp-cli ls prod:/var/www
macscp-cli get prod:/var/log/app.log ./app.log
macscp-cli put ./dist.tar.gz prod:/tmp/
macscp-cli rm prod:/tmp/alt.log
macscp-cli mkdir prod:/var/www/neu
```

Anything without a `name:` prefix is a local path. Whether a session is
backed by SFTP or S3 is not something the caller needs to know — the
stored session decides that through `BackendConnector`.

**Conflicts:** the default is `--on-conflict fail`. `skip` and
`overwrite` must be requested explicitly. A nightly `put` that silently
replaces a production file is exactly the kind of accident no default
should permit.

**Resume** uses the existing engine capability wherever the backend has
it. S3 cannot do append-resume (`supportsAppendResume == false`, M13);
there it retransfers instead of resuming, and `--verbose` says so too.

## Output

- **Only `--json` switches the format:** one JSON line per object
  (NDJSON), so `jq` and `while read` work directly. Without the flag it
  stays the column layout — even in a pipe. Coupling the format to the
  presence of a TTY would be a trap: `macscp-cli ls prod:/ >
  liste.txt` would then deliver something different from the same line
  without redirection.
- **Only the presentation depends on a missing TTY:** no progress
  display, no colors, no prompts.
- **Progress and diagnostics go to stderr**, never to stdout, so that
  `macscp-cli ls --json | jq` stays clean.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success |
| 2 | Wrong invocation syntax (ArgumentParser) |
| 10 | No secret resolvable / login rejected |
| 11 | Host key unknown, cannot be confirmed |
| 12 | Host key mismatch |
| 13 | Connection failed |
| 14 | Path not found / remote side reports an error |
| 15 | Conflict, aborted per `--on-conflict fail` |

## Testing

**Unit (ungated, `macSCPCoreTests`):** `SessionReference` (unambiguous,
ambiguous, unknown, colon in the path, without prefix), `SecretResolver`
(order, skipping an empty source, a failing source aborts, source is
reported), `HostKeyPolicy` (**every** combination of policy, TTY and key
state; mismatch aborts without exception), `TransferPlan` (case
distinctions including conflict).

**Gated (`MACSCP_ITEST`):** roundtrip `put` → `ls` → `get` → `rm` against
the Docker SSH rig and against MinIO, each with a content comparison.

**Security guarantee as its own test:** `--non-interactive` against a
host with an unknown key ends with exit code 11 and **without** a
prompt. That is the guarantee every piece of automation relies on; it is
not left to chance.

## Not in this milestone

`sync`/`mirror` (its own conflict semantics, its own milestone), presigned
URLs via the CLI, transfer between two sessions (S3↔SSH), shell
completion, Linux port.

## Open points for the plan

- Whether the migration runs at app start or on first read access.
- The concrete name of the access group (team ID prefix + identifier).
- Whether `ls` adopts the App's sort order and column selection
  (`FileColumn`) or gets its own, narrower presentation.

## Addendum 2026-08-04 — correction to "sharing the keychain"

The path described above via a shared `keychain-access-group` is
**ineffective** on macOS and has been rolled back. The reason, verified
empirically against the real keychain: `kSecAttrAccessGroup` is honored
only by the *data-protection* keychain, which a query must opt into with
`kSecUseDataProtectionKeychain`. `KeychainSecretStore` does not set this
flag (it does not occur anywhere in the repo), so every query runs
against the old file-based keychain, which knows nothing of access
groups and silently discards the attribute. `KeychainSecretStore(accessGroup:)`
and `KeychainSecretStore()` therefore addressed the same entry — the
group was pure decoration, and the planned migration would not have
moved the entry, it would have deleted it.

**Maintainer decision:** the access-group mechanism is removed entirely
(`KeychainAccessGroup`, `KeychainMigration`, both entitlements files, the
`$(TeamIdentifierPrefix)` substitution in the release script). The
actual mechanism is **per-entry consent**, which macOS enforces itself:
on the CLI's first read access to an entry created by the App, the
system asks; "Always Allow" enters the CLI permanently into the entry's
ACL. That makes unattended operation (cron, CI) work without any
further prompt.

The precondition for this is a **stable code signature** for the CLI — a
freshly built ad-hoc binary has a different identity and gets asked
again. `scripts/release` therefore continues to sign `macscp-cli` with
the Developer ID; from now on it ships **inside the app bundle** at
`macSCP.app/Contents/MacOS/macscp-cli`, where it is covered by the
bundle's signature and notarization and has a stable, documentable path.

The two open points above, on migration and on the access group's name,
are moot as a result.
