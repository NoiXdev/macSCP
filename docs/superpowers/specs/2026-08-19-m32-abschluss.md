## What was implemented

In `applyMerge`, deleting the session slot now depends on the store
write succeeding. If the write fails, the session keeps its binding
**and** its secret; the loop keeps running for the remaining members, and
a message states that sessions kept their own password.

This was documented behavior, not an overlooked bug: the doc comment
said, verbatim, "both are `try?`, so a store-write failure for one
session does not stop that session's secret from being deleted." That
sentence now stands there reversed.

had already carried it as open, because measuring it only read the
order of the calls, not the `catch` beside them. So the lesson applies to
this very spec, not only to the inherited note: **reading a call order is
not a measurement as long as the error branch stays unread.**

Two assumptions of the plan were measured before implementation and
carried the test:

1. `SessionStore.persist` writes with `.atomic` — a read-only *file*
   would have done nothing, because the rename only needs a writable
   directory.
2. `applyMerge` writes the login set first — in the same directory, the
   function would have returned before the loop runs. The two stores
   therefore get separate directories in the test.

requires `displayLabel`, which the plan omitted. Reported during
