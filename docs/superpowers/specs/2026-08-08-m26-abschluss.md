## The counter-check: why the brief's grep is not the evidence

The brief specified a grep for criterion 4 and itself said it expected no
hit. A tool whose expected result is "nothing" cannot distinguish its own
failure from success — exactly the class of error M25 already described one
level up. Two things coincided here:

**First, the line as written in the brief does not even run under `zsh`.**
`grep -rn "\.host\b" Sources/ --include=*.swift` aborts with
`no matches found: --include=*.swift`, because `zsh` tries to expand the
glob before `grep` sees it. An inattentive pass would have logged the empty
output as "no hits" and thereby **booked the broken command as proof of the
accessors' absence**. With the glob quoted it runs.

**Second, even correctly run its result is not conclusive:** 96 hits after
the filter (102 before), all of them `URLComponents.host`,
`SSHConnectionConfig.host`, `StoredSSHConfig.host`, `JumpSpec.host` and
comment text. Not one concerns `StoredSession` — that is the expected
result, it is recorded here, and it proves nothing, because the same 96
hits would stand exactly the same if the four accessors still existed.

### The check that was run instead

A **positive control using the compiler**: a temporary file
`Tests/macSCPCoreTests/M26AccessorProbe.swift` with six accesses on a
`StoredSession` — `host`, `port`, `username`, `authKind`, `keyPath`, `jump`
— followed by `swift build --build-tests`. The command would **compile
cleanly if the accessors still existed**; that is exactly what makes it
evidence. Result:

```
M26AccessorProbe.swift:6:11: error: value of type 'StoredSession' has no member 'host'
M26AccessorProbe.swift:7:11: error: value of type 'StoredSession' has no member 'port'
M26AccessorProbe.swift:8:11: error: value of type 'StoredSession' has no member 'username'
M26AccessorProbe.swift:9:11: error: value of type 'StoredSession' has no member 'authKind'
```

**Exactly four errors, one per deleted accessor — and none for `keyPath`
(line 10) and `jump` (line 11).** The same run thereby proves criterion 4
and criterion 5 simultaneously, and in both directions: the four are gone,
the two are there. The probe file was then deleted;
`git status --porcelain` reports 0 entries, `swift build --build-tests`
runs clean again.

This is the M25 lesson, applied: the compiler measures **mention**. Here
mention was exactly the right question, because a mention after the
deletion no longer compiles — unlike M25's check, where the break said
nothing about correctness.

## Criterion 7 in detail: measurement instead of assertion

Criterion 7 is the only one whose evidence does not sit in a single file:
"every adjustment needed beyond the two rewritten tests is a **finding**." A
green suite does not prove that — an adjustment that weakens an assertion
is just as green as one that only rewrites the access path. So it was
counted.

**The number from Task 2 Step 7: 38 read sites** across 6 test files, raised
as `swift build --build-tests` translation errors after the four
declarations had fallen:
`SessionListViewModelTests` 18, `SessionImportPlannerTests` 7,
`SSHFieldSchemaTests` 6, `BackendApplyTests` 3, `ConnectionViewModelTests` 2,
`StoredSessionTests` 2.

**The measurement in this session.** All `#expect`/`#require` lines removed
from `Tests/` in the milestone diff (39) were matched against all added
ones, after factoring `.ssh?.` or `.ssh.` out of the added ones. Exactly
**three** removed assertions remain without a counterpart:

```
#expect(field?.id == SSHField.password.rawValue)   BackendDescriptorTests
#expect(s.host == "")                              StoredSessionTests
#expect(s.port == 22)                              StoredSessionTests
```

This shows what criterion 7 requires: **36 of the 39 changes assert the same
value as before**, just via `session.ssh?.<field>` instead of the accessor —
e.g. `#expect(session.host == "server.example.com")` →
`#expect(session.ssh?.host == "server.example.com")`. Nothing changed for
healthy data, and that is not the claim of a report but the result of a
line comparison.

The three outliers fall across **two** tests — exactly the two the spec
named in advance ("`anSSHSessionWithoutItsBlockStillShowsAPassword
Field` and its twin"):

1. `BackendDescriptorTests.anSSHSessionWithoutItsBlockStillShowsAPasswordField`
   → `…YieldsTheEmptyBag`. The direction change the spec explicitly
   anticipated; that is criterion 6.
2. `StoredSessionTests.aLegacyPayloadDecodedAsStoredSessionIsSilentlyBlockLess`.
   The twin. Two assertions (`s.host == ""`, `s.port == 22`) collapse into
   one: `#expect(SSHFieldSchema.values(from: s).raw.isEmpty)`. That is the
   only possible rewrite — a blockless record has no "real value" to read
   back to, and `SSHFieldSchema.values(from:)` is the sanctioned successor
   to the accessors. The test keeps its subject (the state M25 called "the
   only documentation of the placeholder in the test suite"), only the
   answer has changed.

**The Task 2 report flagged this second rewrite as a "finding", out of
caution.** The reporting path was correct; the classification is too
strict: the spec announced *both* rewrites in advance, so the second one is
not a finding either, but the intent. As findings in the sense of criterion
7, **zero** remain.

**The drop on load itself changes nothing for healthy data** — the
predicate `$0.kind == .ssh && $0.ssh == nil` matches exclusively the one
shape. `aHealthyNeighbourSurvivesTheDrop` and `aBlocklessS3RecordIsKept` are
the two brackets in either direction.

## The comment wave: the review round's real yield

Task 2's review delivered two **Important** findings, both **stale comments
that this exact change made wrong** — the error class this milestone set
out to remove:

1. **`BackendDescriptor.swift`, `visibleSecretField(for:)`.** The comment
   claimed the nil case "IS the agent case for SSH". Wrong after M26: a
   blockless `.ssh` session **also** returns nil — and
   `SessionListViewModel.updateSession` deletes the keychain entry exactly
   on nil. The case is unreachable (the store discards the record on load),
   but the comment did not say "unreachable", it **denied that the case
   exists**. That is the more expensive error: an unreachable spot can be
   found again; a denied one cannot.
2. **`BackendDescriptorTests.swift`, the `.s3` twin.** Its doc comment still
   claimed "`.s3`/`.webdav`, unlike `.ssh`, has no fallback" — twelve lines
   below the test M26 rewrote.

Both were corrected in `61a86c3`. **The repo-wide grep ordered in the
process found a third copy** that no review had named:
`ConnectionViewModel.swift:800-809` (doc comment on `beginEditing`), which
described the four deleted accessors by name as "fall back to blank/default
values". Also corrected; the fix commit is a pure comment diff, the
re-review was clean.

**This is the lesson of this milestone**, and it is one about comments, not
about code:

> Whoever deletes a declaration must count the prose that describes it. The
> compiler finds every mention in code and **not a single one** in a
> comment. Two of the three wrong spots sat in files the brief had not even
> listed — found only because someone searched for the terms of the old
> claim ("IS the agent case", "unlike `.ssh`", "fallback") instead of for
> the names of the deleted symbols.

Additionally, formally: a comment that declares a case **impossible** is
something different from one that declares it **unreachable**. The second
stays true when the reachability rule is removed; the first quietly becomes
a lie. The three corrected spots now all say "unreachable, and here is the
rule that makes it so".

### Why the keychain orphans are deferred

Not out of convenience, but because they cannot be solved this way:
`SecretStore` only knows save, read, delete — each addressed by **one**
UUID. There is **no enumeration API**, and without enumeration, orphans
cannot in principle be found. The path there runs through extending the
`SecretStore` protocol at a security-critical point. That is a separate
pass with its own decision, not a minor cleanup.

### The import fix, and what was wrong about the original finding

The rule is: **the planner rejects exactly the shape the store would
discard anyway.** Not a second, independent judgment of what "complete
enough" means — the load logic is factored out into
`SessionStore.dropsOnLoad`, and `load()` and the planner call the same
function. Whoever tightens the store rule automatically tightens the
planner rule. The check builds the candidate via the same `makePlanned`
the real path uses, so nothing can diverge between plan time and load time.

**Reported and skipped, not failing the file.** That is the house rule from
M23, already applied three times in this path
(`storeFailures`, `passwordFailures`, the login-set twin). The only
whole-file abort left in the code is `unsupportedVersion` — a judgment
about the **format**, not about the content.

**Two details of the original finding were wrong**, established during
verification before implementation:

- The keychain orphan arises **only if the file carries a secret**. Without
  a secret, only the false report remains.
- The record is **immediately** invisible, not only at the next launch:
  `applyImport` ends with `reload()`, which goes through the read path. So
  the "1 imported" message appears while the sidebar already no longer
  contains it — sharper than claimed.

The login-set import does not have this hole: its codec declares the
affected fields as non-optional, a file without them already fails at
decoding.

**Not fixed along with it, deliberately:** a bag with only `keyPath`, and
an entry saved by its jump fields, each produce a visible but
unconnectable session. A different error class — they are visible and
deletable, so not the problem this was about.

**Not extended, deliberately:** `.s3`/`.webdav` remain importable. The
obvious tightening ("reject every incomplete entry") would have broken two
tests that deliberately pin that a **real** pre-M21 WebDAV export without
columns keeps importing. These are files that shipped builds wrote; discarding
them over a hand-edit gap would have been a regression against real user
data.

### What the review found in it

Eight findings, not one of them in the logic — four of them comments the
fix itself got wrong, including one that declared a case "impossible" that
the report of the same commit listed as open.

The most important was a **test that proved nothing**: the end-to-end test
was meant to show that no orphan arises anymore, but checked `peek(id)` for
the one ID it had computed for itself — and after the fix, the loop that
writes any secrets at all runs zero times. Green thus proved "under this
one ID there is nothing", not "nowhere is there anything." Fixed via an
enumeration in the test double. **A test whose assertion is trivially
satisfied after the fix is not a regression guard, it is a reminder of one.**

Plus an invariant test for the coupling itself: **no planned import
satisfies `dropsOnLoad`.** Without it, someone could later write a second
condition straight into `removeAll` instead of into `dropsOnLoad`, and the
divergence would be back without anything turning red — the purpose of this
fix, unsecured.

A number in a comment ("removing the guard breaks exactly two tests") was
**remeasured rather than carried over** on this occasion, and rose to
eight. A number in a comment is a measurement, not a memory.

### The three minor points

- **Test gap closed.** `updateSession` deletes the keychain entry exactly
  when `visibleSecretField` returns nil. For a blockless `.s3`/`.webdav`
  record, that depends **entirely on the fact that no secret field of
  either protocol declares a `visibleWhen`**. Whoever later adds one — an
  "anonymous" toggle for WebDAV, say — turns a rename into silent secret
  loss. Now pinned per protocol, each seen red against an experimentally
  inserted `visibleWhen`.
- **Eight form accessors into the test target.** The backlog entry read
  "eight dead shims" — half right: in production code none has a caller,
  but the tests call them at 69 sites. "Delete" would have rewritten 69
  call sites to the subscript form, without making a single error
  impossible. Moved instead of deleted: the production API shrinks by
  eight members, no call site changed. The check "no production caller" ran
  via the **compiler**, not via grep — the names collide with
  identically-named fields on other types.
- **`JumpRestoreResult.restored`** now states on the field itself that it
  counts referencing sessions, not restorations performed. The type is
  `public`; whoever uses it from outside reads the type, not the body.

## Addendum: the two import shapes are not a finding (2026-08-09)

The cleanup pass listed them above as "not fixed along with it, different
error class." On closer inspection they are **not a bug but the correct
behavior**, and the maintainer confirmed this as a decision on 2026-08-09.
They are therefore struck from the backlog, not deferred.

**The two shapes.** A field bag carrying only `keyPath` passes the
`!fields.isEmpty` gate; `SSHFieldSchema.apply` then writes `host: ""`,
`port: 22`, `username: ""`. An entry carrying only jump fields gets a
`StoredSSHConfig` with an empty host that the jump can hang off of. Both
survive the drop on load, because `ssh` is not nil.

**Why this is correct.** The entry keeps its name and everything the file
actually contained — the key path, the jump data. The session is visible,
editable and deletable, and `StoredSessionConnectionConfig.build` does not
fail silently but with `incompleteConfiguration(field:)`, which **names the
missing field**. The user fills in the host, instead of recreating the
entry.

The difference from the blockless `.ssh` record, which is rejected, is
exactly this: **there the user gets nothing but a false report** — the
store discards the record immediately, the session never appears, and a
shipped secret becomes an unreachable orphan. Here the user gets data he
can keep and repair. Rejecting it would mean taking something away from
him.

**The remaining gap, deliberately left open:** nothing is said about the
incompleteness at import time; the user only learns of it when attempting
to connect. A note in the result message was considered and rejected — it
would be one more line in the alert for a case the connection attempt
already names precisely.

**The lesson.** The finding came from the same round as the real hole and
was therefore filed in the same drawer. "Creates a session that does not
connect" sounded like the same problem — but is the opposite: in one case
the user loses data without being told; in the other he keeps it and is
told what is missing. **Two symptoms that sound alike need to be checked
separately before they get the same treatment.**
