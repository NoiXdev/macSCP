## The backstory in one paragraph

On the same day, a login-set slot fix was **withdrawn** (`479d018`).
Its target was the **stale slot**: a session bound to a login set keeps its
old password in the keychain. Four adversarial reviews found four ways in
which the fix, in the process, destroyed the **only** copy of a secret. The
follow-up investigation refuted the goal itself: the stale slot is the
**mild** condition — nothing is lost, and connect honestly refuses.
Dangerous are two spots the withdrawn fix **never touched** and that were
already there before: of five binders, exactly two delete a keychain slot
(`applyMerge` and the jump binding via `cleanOrphanedJumpSlot`), and neither
of the two asked any condition before doing so. M28 makes them ask — and
explicitly leaves the three non-deleting binders and the stale slot
**untouched**.

### Criterion 1 in detail: why the wording does not hold, and should not

The spec demands "set without secret, merge runs, `storedIDs` of all members
unchanged". `applyMerge` does **not** behave that way: if the group holds
nothing transferable — no slot, or only slots holding `""` — the merge goes
through **and deletes the member slots**. `memberSlotsHoldingOnlyTheEmptyStringLet
TheMergeCarryNothing` shows exactly that (`storedIDs` from `[a, b]` to
empty).

That is the deviation the plan disclosed, not carelessness:
**`applyMerge` transfers**, and whatever gets deleted there holds, by
definition, nothing that could be lost. The criterion's purpose — no loss —
is met; its wording was aimed at the wrong binder. Anyone who took the
wording literally would be handed empty slots that protect nothing.

### Criterion 8 in detail: the text is not testable

The new line is produced in `LoginSetsSheet.importResultText`, a `private`
method in the App target `MacSCPApp`. **The package has exactly one test
target, `macSCPCoreTests`** (`ls Tests/` → only this directory). A test over
the generated text is therefore impossible without first pulling the
formatting out of the view. Same structure, same finding as M27's criterion
10 — and the same consequence: **whoever rebuilds this line tomorrow breaks
criterion 8, and nothing goes red.** Listed below under what remains open.

## The deviation from the spec: one rule became two

The spec formulates **one** rule for both binders: "A binder that deletes
asks the same question as the connection path." That did not hold up during
planning, and the plan disclosed it instead of smoothing it over:

- **The jump binding** deletes a slot that **nothing transfers** — the old
  bastion slot is the only copy. There, the coverage question is the right
  one.
- **`applyMerge`** does transfer. Its defect was not the missing question,
  but the **swallowed read**: `try?` turns "not readable" into "nothing
  there", and then it deletes. The coverage question would not have
  improved anything here; a **throwing** read would have.

**What this says about generalizing.** The spec was correct in substance
and one level too coarse. "Both delete, so both need the same question" is
a commonality at the level of *action*, while the defect sits at the level
of *where the value comes from*: does this transfer something, or not? A
rule that lumps two spots together must attach to the trait that produces
the defect — not to the one both happen to share. The cost would not have
been harmless: a coverage question in front of `applyMerge` would **not**
have replaced the throwing read, and the loss path would have stayed open
under a plausible-looking guard.

**The second deviation and its correction.** From the same spec passage, the
plan concluded the managed-key probe would be "needed nowhere". That is
true for the **coverage question** (a `.privateKey` set shows `passphrase`,
not required, the "needs nothing" branch carries the case) and **false for a
deletion decision**: a binder that deletes on that alone removes the
passphrase slot of a session whose key is encrypted and whose set holds
nothing. **The task-1 review caught this**, the plan was corrected
(`3ce47f7`), and task 3 has combined both questions ever since. A claim
that holds for one purpose does not hold for every purpose.

## Eight things this milestone records

### 1. The plan knew one of four loss paths in `applyMerge`

What was briefed was the **swallowed read**. The reviews found three more:

1. **An empty string counted as "has a secret".** `save` creates a slot for
   every manual, non-agent session, `""` included — an unencrypted private
   key leaves exactly that. A passphrase never enters the planner's
   grouping key, so the empty member could stand **before** one with a real
   passphrase. Taking it as the source carried `""` onto the set and then
   deleted the real passphrase — the group's only copy. **With no keychain
   error at all.**
2. **The window between two reads** (see point 2 below).
3. **Members with DIFFERENT secrets** were silently folded into one. Two
   `.privateKey` sessions with the same username and key path but different
   passphrases group together — neither passphrase nor host is part of the
   planner's grouping key. Maintainer decision 2026-08-09: **abort**. A
   login set is, by definition, *one* credential; if the members hold
   different ones, the set could serve at most one — so the merge produced
   a broken state **and** destroyed a secret in the process. The rejection
   takes nothing away; it declines a merge that could never have worked.

> **Each of these three was found by a review, none by a test —**
> **not even by the tests written in the same round.**

This is exactly the pattern of the four withdrawn rounds, here for the
fifth time. Tests check the assumptions under which they were written; a
loss path the author did not see is also absent from their tests. The
checking authority has to come from outside.

### 2. The best fix eliminated a class instead of guarding it

The carry read twice: once to choose the source, once to actually transfer
it. Fix round 2 turned that into **one** read — the value found *is* the
value transferred. With that, gone were

- the TOCTOU gap between the reads (the keychain could lock in between, the
  slot could change in between, and the **second** read's answer counted),
- the second knob on the test double that round 1 had had to build
  specifically, just to represent "keychain locks BETWEEN the reads" at
  all,
- and a test that only checked that knob.

Fewer lines, fewer tests, one error class removed instead of guarded.
**A guard needs a guard of its own down the road; an eliminated state does
not.**

### 3. Task 3 refused the brief's alternative and proved a third answer

The brief posed the managed-key question as binary: accept the probe or
not. The implementer derived a third answer from the code, and the review
verified it: a set-bound jump resolves via `LoginResolver.resolveJump` →
`sshLogin(from set:)` — **exactly one read, namely of the SET's slot**. The
two call sites of `ManagedKeyPassphrase.resolve` (the connect button in the
form, the fill path in `ContentView`), by contrast, write the connection
form's **own password** from its own key path. The slot of a managed key
therefore **never** lies on the jump path; the probe could not have saved
the jump even if it held the passphrase. The guard therefore asks the only
piece of evidence that exists at this spot — the set's slot — and an empty
one means "cannot determine", so **do not delete**.

> **A brief that offers two options has not thereby proven there are**
> **only two.**

### 5. A finding beyond M28, for the backlog

**Under `swift test`, `CoreL10n.string` returns the key itself for EVERY**
**Core key.** The task-2 review proved this empirically with a throwaway
package that rebuilds the bundle layout; re-verified structurally for this
report: `macSCP_macSCPCore.bundle` sits in `.build/debug/`, **not** in
`macSCPPackageTests.xctest` (`find … -name "*.bundle"` there gets no hits),
and the remaining two candidates of `CoreL10n.bundle`
(`Bundle.main.resourceURL`, `Bundle.main.bundleURL`) point, under
`swiftpm-testing-helper`, into that helper's own directory. So the `.main`
fallback kicks in, and `localizedString(forKey:value:)` returns the key.

Consequences:

- Dozens of existing `#expect(error == CoreL10n.string(…))` assertions
  across several test files compare **key against key** and cannot fail.
- Nothing in the suite would catch a Core key misspelled in code, missing
  from `en.lproj`, or whose placeholders do not match its format arguments.
  `LocalizableStringsTests` only compares key sets **between** languages,
  from disk.
- **`CoreL10n`'s doc comment claims the opposite** ("In the test target
  `Bundle.module`'s own search succeeds normally, so tests exercise the
  same lookup as production code") and is therefore wrong.

A test that reads `en.lproj` via `#filePath` and checks the code's keys as
a subset of it would close this gap and would run under `swift test`.
**A pass of its own, not M28.**

### 6. The jump binding to a foreign-kind set — found at closeout, closed in T5/T6

While proving criterion 6, a gap surfaced. The first version of this report
reported it as open; the maintainer decided to close it **within the**
**milestone**. The finding, in its wording from back then:

The jump section's set picker lists **all** login sets, unfiltered by
`kind` (`ConnectionFormView`, `ForEach(sessionList.loginSets)` — the
session's own set picker, by contrast, filters with
`.filter { $0.kind == kind }`). `LoginResolver.resolveJump` likewise
accepts a set-bound target with no `kind` check and passes it to
`sshLogin(from set:)`. And a WebDAV set is built by
`WebDAVFieldSchema.loginSet` with `authKind: .password`.

This yields: a **WebDAV set without a secret** counts as "covered" per the
spec table (maintainer decision from M23: anonymous shares stay
connectable), `setCoversItsLogin` answers `true`, the private-key arm does
not fire (`authKind == .password`) — **and `cleanOrphanedJumpSlot` deletes**
**the old bastion slot.** The jump then resolves via the WebDAV set's empty
slot: password gone, jump unable to log in. The same in a different shape
for an **S3 set with** a secret: covered, slot deleted, and the jump from
then on authenticates with a Secret Access Key as its SSH password.

**This is exactly the error class M28 is built against**, surviving for
foreign-kind bindings — and for the same reason as the managed-key gap that
task 3 closed: the coverage question asks "does **this set** need a
secret", while the deleting site needs to know "does **this login** lose**
**something it needs**". The distinction was drawn for the private key, not
for the case `set.kind != .ssh`.

**Closed at all three spots the finding named as candidates** — because
they cover different states and none replaces the other:

- **T5** (`28002dd`): a third arm in the guard. `jumpSetDemonstrablyCovers`
  `ItsLogin` refuses the deletion when `set.kind != .ssh` — the bastion
  slot stays, no matter how "covered" the foreign-kind set looks.
- **T6** (`9cc5a78`): a throw in the resolver (`LoginResolveError.jumpSetNotSSH`)
  plus `JumpLoginSetEligibility` as a `kind` filter for the picker. The
  filter governs what can be **newly** chosen; the throw covers what is
  **already on disk** and never passed through the filter.
- **T7** (`f9c9979`): the same `kind` guard in front of the App-side fill
  path — see section 7, because that is where the actual hole sat.

### 7. The fifth credential path — what only a whole-branch review could find

The whole-branch review over `d657995..9cc5a78` reported **Critical**: a
WebDAV or S3 password could reach an SSH bastion host. Not a loss — a
**disclosure**, and thereby heavier than anything M28 was built against.

The chain ran across both layers and through four states:

1. A session whose jump is bound to a foreign-kind set — either as legacy
   state, or freshly created because the login-set import reuses `id:`
   `match.id` on replace while `fileSet.kind` is passed through unchecked:
   an import can turn an existing SSH set, under the same ID a jump still
   points at, into `.webdav`.
2. `ContentView.resolveSelectedJumpLoginSet` → `fillJumpForm` read the
   set's keychain slot into the form **with no `kind` check**. No
   `LoginResolver`, hence also no `.jumpSetNotSSH`.
3. A submit that failed validation left the values in place
   (`endEditing()` does not run on this path).
4. The jump login mode was a **bare stored property**, without the
   cleanup rule that both `selectJumpSourceMode` and `selectJumpAuthChoice`
   have — whose own doc comment describes exactly this damage in words.
   Switch to "Manual", save: `buildJumpSpec` writes
   `loginSetID: nil` and a fresh `secretID`, and the WebDAV password
   ends up in the session's **own** jump slot. From then on `resolveJump`
   sees no set at all, and the refusal built in T6 never fires.

Closed in T7 on both halves: `kind` guard before filling (`f9c9979`),
cleanup on mode switch (`b42ba58`), picker routed through the switch
(`e78ae99`).

**Why no task review saw it.** Each of the seven task reviews checked its
own diff. But the path consists of four parts, **none of which is wrong on
its own**: a fill path with no `kind` question (harmless as long as
bindings are same-kind), a submit that keeps the form on failure
(intentional), a property with no cleanup (unremarkable next to two
siblings that do clean up), a save that persists manual values (correct).
Only the diff **as a whole** shows the chain. This is the same finding as
in M24–M27, here for the fifth time: **the whole-branch review is not a**
**repeat of the task reviews, it sees a different class.**

### 8. The App target has no test target — and here that is not a formality

While securing section 7, the `kind` guard was experimentally **removed**
**entirely**. The full suite stayed **green**. `Tests/` contains exactly
one directory (`macSCPCoreTests`); `MacSCPApp` is an executable target with

## Deferred minor items (from the ledger, for triage)

- **Agent group with conflicting leftovers.** An ssh-agent group has no
  visible secret field at all; its members are supposed to have no slot,
  but `save` deletes with `try?`, and a rejected delete leaves one behind.
  If two such leftovers hold different values, the merge today rejects
  with "they store different credentials" — for a login that has none at
  all. **Safe direction, confusing message.** The clean fix is the same
  schema question task 1 built.
- **`applyImport` still unconditionally deletes the old jump slot of a**
  **replaced record** when the planner assigns a fresh `secretID`. Same
  shape as the defect just fixed — with the difference that there the user
  consented to the replacement.
- **Done in `603c3dc`:** the test identifier split across a line break
  (`saveJumpSwitchingManualToSessionDeletes` /
  `JumpSecretSlot`) and three line-number citations in comments.
- **`deleteLoginSet` reports a failed read at the wrong spot.** The abort
  yields `secretFailures: 0`, and `LoginSetsSheet.deleteSelected` only sets
  its inline message when `secretFailures > 0`. In the sheet, the deletion
  therefore looks like a silent no-op; the red line appears via
  `errorMessage` in the sidebar, i.e. **only after closing**. Nothing is
  lost, but the message does not appear where the user is looking — the
  existing store error path already has the same gap.
- **The destination picker (not the jump picker) has no `kind` guard.**
  `ConnectionFormView`'s login-mode switch for the **connection**
  **destination** is a raw binding, and `resolveSelectedLoginSet` does not
  ask about `kind`. Consequence-free today, but only by a namespace
  coincidence: a foreign-kind set's secret ends up under its own prefix
  (`webdav.password`), which an `.ssh` form never reads and
  `descriptor.apply` never persists. **Safe by accident, not by design.**
- **The FR and PL translations** of the three new keys are by the
  implementer and **not checked by a native speaker** — the same standing
  reservation as for the rest of FR/PL in this project.
- **From T1:** no test pins the literal/untrimmed rule for a secret made of
  pure whitespace; the "no read" ordering is pinned only for the agent row,
  not for the two rows with an optional secret.
