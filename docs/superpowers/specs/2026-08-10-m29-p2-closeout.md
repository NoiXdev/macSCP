# M29-P2 — Closing Report (The Submit Path Moves to Core)

**Status:** completed 2026-08-10. HEAD before this report: `3d49264`.

M28's only Critical — a WebDAV or S3 password could reach an SSH bastion
host — was warded off by a `private func` on a SwiftUI view that **no test
held**. P2 moves this decision to Core. Three resolutions
(`resolveTargetLoginSet`, `resolveJumpLoginSet`, `resolveJumpSession`) and
one coordinator (`prepareForSubmit`) now live there as `SessionListViewModel`
methods, where the existing suite reaches them. They return **cases, not
text** (`SubmitRefusal`); each case carries its own field to highlight. The
app now only translates.

The **only intended behavior change**: the target picker gets a `kind`
guard it never had.

Spec: `2026-08-10-m29-p2-submit-path-design.md`.
Plan: `../plans/2026-08-10-m29-p2-submit-path.md`.

## Two defects in the plan, found by Task 2

Both concerned the instructions themselves, not the code; both are
corrected in the plan in `1e3bce1`. They belong here because the second one
violated a binding requirement of this project.

1. **The rollback order destroyed unversioned work.** The plan had the
   mutation probe run *before* the commit and afterward `git checkout --`
   on the Core file. On the first pass, the implementation was not yet
   committed — the command thus did not revert the mutation, but
   **deleted the entire ported implementation** on `HEAD`. Exactly that
   happened. The implementer recreated the file and switched to
   commit → probe → revert; only in that order does the command mean what
   the plan says. Task 3 adopted the corrected order.

2. **The assertion shipped with the plan let a secret reach the failure
   message.** The plan wrote `#expect(form.jumpPassword.isEmpty)`. Swift
   Testing expands the receiver, so the first trial run printed the
   **value** of the credential into the failure message — forbidden by the
   binding requirements. Fixed via the pattern already present in the
   project: hoist first into a `let … = form.jumpPassword.isEmpty`, then
   check the `Bool` (`SessionListViewModelTests`, "Compared as a Bool so
   no secret can reach a failure message"). The probe still shows **that**
   the credential reached the form — it names the fact instead of quoting
   the value. The same hoist was applied to the three other `jumpPassword`
   assertions.

> **An assertion shipped with the plan is a hypothesis, not a result** —
> the same lesson as in P1, here with a security requirement at stake.

## False comment claims: six, and where they came from

**Addendum:** this section counted **four** in the report's first draft. A
subsequent whole-branch review found two more — both miscounts in test doc
comments from Task 2 that stayed undetected while this very report was
being written. Recounted and added below: the correct number is **six**.
The gap confirms the milestone's own lesson from the other side — even the
tally that preaches "recount" must itself be recounted.

**Four were newly written in this milestone and were already wrong when
written.** Two of them come verbatim from the plan's code blocks — checked,
both sentences appear in the plan document itself — neither is an
invention of the implementer. The other two are the implementer's own doc
comments from Task 2, for which the plan has no template — checked,
neither sentence appears in the plan document.

1. **`SubmitRefusal`'s doc comment** (from the plan): claimed the field
   mapping had been "scattered across four `catch` branches in the view".
   Recounted: **seven** rejection sites across **three** functions, of
   which only four are actual `catch` branches, the remaining three
   `guard`-`else` exits. Wrong on both axes. Replaced with a
   number-free phrasing that cannot rot (`c015c65`).
2. **`SessionListViewModel+Submit`'s doc comment** (from the plan): claimed
   the namespace separation holds "only as long as no two backends share a
   field ID". Backwards: `SSHField` and `WebDAVField` already declare
   `username` and `password` **both**. What actually separates them is the
   hand-written `namespace` string per backend, whose uniqueness is checked
   nowhere. Corrected in the same commit — found by the implementer
   themselves, after the review demanded that *every* count and
   completeness claim in both new files be re-measured.
3. **`theJumpSetHalfIsANoOpOffInSessionModeAndInManualMode`'s doc comment**
   (Task 2, `efecda2`, no plan template): claimed "the three no-ops of
   the set half". Recounted: the test runs **four** `#expect` blocks —
   off, session-bound, manual, unselected — because `resolveJumpLoginSet`'s
   `guard` checks four conditions, not three. Found by the whole-branch
   review after this report; corrected in the following fix wave to a
   number-free phrasing that names the four cases instead of counting them.
4. **`theJumpSessionHalfIsANoOpOffAndInManualSourceMode`'s doc comment**
   (also Task 2, `efecda2`, no plan template): claimed "the two no-ops of
   the session half". Recounted: the test runs **three** `#expect` blocks —
   off, manual source, unselected — because `resolveJumpSession`'s `guard`
   checks three conditions, not two. Same location and same fix as above.

**Two more were pre-existing and only became wrong through this

5. The doc comment on the `kind` setter in `ConnectionViewModel`: "…
