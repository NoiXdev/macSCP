Reported bugs, with the state as measured against the code. **No fixes, no
designs** — what is here is finding and open question.

## B-1: Connecting to a non-responding host blocks the app

**Reported:** 2026-08-20, maintainer. When connecting to a host that does
not respond, the app is unusable until the timeout expires.

### Measured

**The timeout is 30 seconds, and nobody sets it.** Citadel's
`SSHClient.connect(host:port:…)` has a default value
`connectTimeout: TimeAmount = .seconds(30)`. `CitadelFileSystem` calls this
overload at **two** places — for the jump hop and for the target — and
passes the parameter at **neither** of them. NIO's own default would be
10 seconds; Citadel overrides it to 30.

Across the whole SSH and session code there is **no** dedicated timeout
option: the only hit on `timeout` outside comments is the SSH-agent path.

**There is no setting for it** and **no way to cancel** while waiting.

### Answered on 2026-08-28: an operator-facing bug, not a concurrency bug

Measured with `Tests/macSCPCoreTests/ConnectMainActorLivenessTests.swift`
(`fd87168`) — a ticker pinned to the main actor, whose largest gap between
two timestamps carries the verdict, not its tick count.

|Question|Answer|
|—-|—-|
|Does the main actor block?|**No.** With a target whose accept queue is full (the kernel drops the SYNs), the connect attempt hung for the full period while the ticker ran 68 times; largest gap 31 ms against a 28.8 ms baseline.|
|`AgentBackedPrivateKey`'s semaphore?|Blocks **the caller** (414 ms against a 400 ms deadline), but is **unreachable**: `signature(for:)` has zero call sites in `Sources/`, and NIOSSH calls it on an event-loop thread during user authentication — i.e. after TCP and key exchange, which a dead host never reaches.|
|Name resolution or TCP?|**Both** are covered by `connectTimeout`. NIO arms the deadline in `resolveAndConnect()` before the first query; measured, a connect attempt with a hanging resolver failed after 0.401 s against a 400 ms deadline.|

**The reason is structural, not incidental:** `ConnectionViewModel.connect()`
awaits a non-isolated `@Sendable` connector, and that `await` leaves the
main actor. A connector that blocks its own thread for 600 ms measurably
did not run on the main thread in the counter-check.

That confirms the entry's original hypothesis and settles the question:
there is nothing to unblock. What was missing was purely what the user
sees and can do in the meantime — and the adjustable deadline, the
cancel, and the error view with "Reconnect" have since largely delivered
that.

**The instrument was checked against itself.** A ticker that keeps
running proves nothing as long as it *cannot* show a gap: a test
deliberately blocks the main actor and demands the gap (414 ms against
400 ms). Two planted mutations turned red. In the process, two real holes
in the instrument surfaced, both found by a block that stayed green — a
block before the first timestamp, or one still running at the last, leaves
no measurable gap. Both ends are closed now.

**What stayed open:** a real hanging nameserver (needs root privileges or
resolution outside this machine; measured with a substituted NIO resolver
on Citadel's path). And a side finding that does not belong here but is
measured: **the test harness stalls its own main actor for up to 4.68 s at
a stretch** — pre-existing, not reproduced by this suite, unexplained. See
the M20 hang in the backlog.

### What is not yet measured — and the actual question

Whether the main thread really **blocks**, or whether the app merely sits
for 30 seconds in a state that feels like a freeze (modal, disabled
controls, no cancel), is **open**. That decides whether it is a
concurrency bug or an operator-facing bug — and those are two entirely
different fixes. To clarify before anything is changed:

- Does the main thread measurably block? (A spinner that stops is the
  proof; one that keeps turning refutes it.)
- Notable along the way: `AgentBackedPrivateKey` waits with
  `semaphore.wait(timeout:)` — a **blocking** wait in an otherwise
  asynchronous path. It sits behind the TCP connect and therefore
  presumably does **not** explain the reported case, but is worth a look
  while already there.
- Where exactly does it hang: name resolution or TCP connect? NIO's
  `connectTimeout` covers the connect; it does not necessarily cover name
  resolution. A host whose DNS hangs behaves differently from one that
  swallows packets — both cases need to be produced separately.

### Foreseeable parts of a solution

Regardless of the measurement's outcome: **cancelable** is the core of
it. Even a short timeout is the wrong answer if the user can do nothing
in the meantime. Plus a sensible default and a setting.

**Related to** `2026-08-20-backlog-sitzungen-tabs-seitenleiste.md`, point
A1 (error view in the tab with "Reconnect") — that is the presentation of
the same process, and both should be designed together.

## B-2: An aborted download does not close its SFTP handle

> **Fixed on 2026-08-27** in `42ec1b0`. The investigation below stands
> because it records two things that outlive the fix: the
> `CancellationError` branch in `readStream` is **dead code** for the read
> (NIO's `get()` is not cancellation-aware), and
> `AsyncThrowingStream(unfolding:)` does not call its closure again on
> cancellation — it releases it instead. Whoever cleans up there should
> know both.
>
> **Correction of the hypothesis the investigation started from:** it was
> assumed that user cancellation was covered and only an error on the
> destination side leaked. Measured, **all three** paths leaked, user
> cancellation the most frequent.

**Logged:** 2026-08-26, as a side finding while answering the last
`Sendable` warnings. Not touched, because it is neither a warning nor a
data race — it belongs in its own decision.

If a consumer aborts the stream from `CitadelFileSystem.readStream`
**before EOF** — i.e. the ordinary case of "cancel a download partway
through" — nobody calls `file.close()`. Citadel reports this itself during
cleanup:

> `SFTPFile deallocated without being closed first`

The handle thus hangs on the far side until the connection drops. A user
who cancels several transfers accumulates open handles on the server —
and servers typically cap that.

**To clarify before taking this on:**

1. How often does this really happen? The cancel path is `cancelAll` and
   canceling a single transfer — both are everyday, not an edge case.
2. Where does the close belong? The stream's `onTermination` handler is
   the obvious answer, but then it runs in a different task from the
   read; that is exactly the question the three other backends also have
   to answer.
3. Does it affect the other backends equally? Local, S3, and WebDAV each
   have their own resources hanging off the stream.

**What it is not:** not a data race and not a security shortcoming. The
transfer path itself was re-checked on the same occasion — exactly one
consumer drains the stream, across all four backends.
