### 3. The new candidate sorted to the front — **everything stays green**

The four candidates in `L10n.bundle` reordered so that the newly added
`Bundle(for:)` candidate is **first** rather than last. `swift test --filter
L10n`:

```
✔ Test run with 5 tests in 2 suites passed after 0.008 seconds.
```

This proves the gap deferred in the ledger: **no test pins the
order.**

**What the probe proves — and what it does not.** The original sentence at
this spot claimed that moving it to the front breaks the
no-behavior-change assertion, because in a real `.app` `Bundle(for:)` would
then decide instead of `Bundle.main.resourceURL`. **That is wrong.**
`MacSCPAppKit` is statically linked into the executable `macSCP` (`otool -L` on
`dist/macSCP.app/Contents/MacOS/macSCP` names only
system frameworks, no own `.dylib`; `nm` finds 8061 `MacSCPAppKit`
symbols in the executable itself). So `Bundle(for: BundleFinder.self)`
in the running `.app` **is** exactly `Bundle.main`, and
`.bundleURL.deletingLastPathComponent()` is the directory that contains
the `.app` — no resource bundle sits there. The candidate moved to the front
thus reaches into nothing, and the loop still falls through unchanged to
`Contents/Resources/`.

Measured rather than derived, with a throwaway binary outside the repo
(a statically linked Swift program with a local `BundleFinder`
class, once bare in a directory, once inside an `.app` shell):

```
CASE A: bare executable in bin/ (model for .build/release)
  Bundle(for:) === Bundle.main? true
  Bundle(for:).bundleURL.del  = …/bundleprobe        (parent directory)

CASE B: same binary in Probe.app/Contents/MacOS/ (model for the App)
  Bundle(for:) === Bundle.main? true
  Bundle(for:).bundleURL      = …/Apps/Probe.app
  Bundle(for:).bundleURL.del  = …/Apps               (parent directory)
```

It also stays without consequence under `.build/release`: `ls .build/release` contains
`macSCP_MacSCPAppKit.bundle`, `ls .build` does not contain it — the candidate
moved to the front points one level too high there as well and likewise
reaches into nothing.

**The reordering is thus behavior-neutral in every real deployment.**
The missing pin is a readability guard, not a correctness safeguard:
it would record that the order is *deliberately* chosen, and would keep a
later refactor from relying on it. Reverted,
`git status --porcelain` empty.

### Criterion 1 in detail: what is not proven here

The app was **not launched**. `package-app` proves that an
`.app` bundle assembles correctly and that the resource bundle sits under
the new name within it — not that the running app shows the same texts
as before. The silent fallback was the milestone's biggest risk, and
exactly that risk path (does the running `.app` find its bundle?) is the
one path no test in this package can reach. The evidence for that is
indirect and readable in the code: `package-app` copies the bundle to
`Contents/Resources/`, which is exactly `Bundle.main.resourceURL` —
the **second** candidate on the list, which returns before the fourth is
ever checked. (The fourth is still built regardless: the candidate list is
an array literal, all four URLs come into existence on every launch. Only
it is not *evaluated*.) That is a derivation, not a measurement. **The
maintainer's visual check is still outstanding.**

## Five Things This Milestone Records

### 1. The prediction "some existing tests will go red" was structurally impossible

The plan had planned for a side effect that could not exist. Assertions of the
form `#expect(error == CoreL10n.string(key))` send **both
sides through the same lookup**. Before the fix, both sides returned the
key text; afterward, both returned real text — the meaning of the comparison
never changes in the process. No test could possibly have flipped, and none
did: two full runs after the Core and after the App fix, each with
**zero** `✘` (counted in the Task 2 report, not reproduced here — this
session's runs show the same state at the end of the chain).

The premise held **halfway**, though: the App layer really did not
resolve under `swift test`, every lookup returned its English
`defaultValue`, and that looked correct in an English screenshot.
The finding was real, the predicted consequence was not.

> **A true finding and the consequence derived from it are two separate
> claims.** Proving the first does not prove the second.

### 2. A claim had to be retracted mid-milestone

The same assertions had been described as "vacuous" and "could not
fail" — in the plan, in the task brief, in the commit body of `ad8e536`, and
in two doc comments. **False.** The production code returned
`CoreL10n.string(A)`, the test expected `CoreL10n.string(B)`; what was
compared was thus key A against key B, and a wrong key very
well did go red.

What was untested was something else and narrower: **whether a
key maps to real text at all.** A key that no catalog declared was
indistinguishable from a declared one — both returned themselves. Exactly
that is what the new guards close off.

Corrected in `e3e7158` in `CoreL10n.swift` and `CoreL10nTests.swift`; the
words "vacuous," "could not fail," and "compare a key against itself" no
longer appear there. **The commit body of `ad8e536` still carries the
overly strong sentence** — history is not rewritten, and this paragraph
is the correction it should be read against.

### 4. A proposed test was algebraically useless, and that was proven

The coordinator had supplied a ready-made replacement for
`theUpdateMessageNamesBothVersions`: compare `message(latest: a, current: b)`
against `message(latest: b, current: a)` and expect inequality. The
implementer built it in, then — as the same instruction required —
injected the error it was supposed to catch (swapped the two arguments of
`String(format:)` in the `.updateAvailable` branch) and ran the test.
**It stayed green.**

The justification is not empirical but a calculation. Let `T(a, b)` be the
application of the template. Correct is `f(a, b) = T(a, b)`, the injected
error is `f(a, b) = T(b, a)`. The proposal compares `f(a, b)` against
`f(b, a)`. Under **both** definitions this yields the same pair
`{T(a, b), T(b, a)}`, only in a different order — so the inequality holds
always when `a ≠ b`, and says nothing about the correctness of `f`. **Swapping
the inputs of a two-argument function and swapping its output is the
same operation**; a test that holds both against each other cannot
separate the two cases.

Replaced by an assertion without permutation: rebuild the expected text
from the same `L10n` template, with `latest` before `current`, and hold it
against the real output of **the same** call. With the same injected
error this goes red:

```
✘ Test theUpdateMessageNamesBothVersions() recorded an issue at UpdateAlertContentTests.swift:81:9: Expectation failed: (message → "Version 1.1.0 is available (installed: 1.2.0)") == (expected → "Version 1.2.0 is available (installed: 1.1.0)")
```

(carried over from the Task 3 report; not reproduced in this session.)
It stays language-independent, because `String(format:)` resolves
`%1$@`/`%2$@` positionally against the argument list — a translation is
allowed to reorder the placeholders.

> **An assertion supplied by the coordinator is a hypothesis, not a
> result.** It gets proven red-and-green like any other.
