## The protocol counter-check

```
$ git diff b6fb80b..HEAD -- Sources/macSCPCore/Sessions/SecretStore.swift
(empty)
```

The spec's commitment — "**the `SecretStore` protocol stays unchanged**" —
is thereby proved: a protocol change would necessarily have to appear in
this file, because that is where the `protocol SecretStore` declaration
lives. If the diff is empty, the file is byte-identical, and then the
declaration cannot have changed.

**This section's original justification — "harder than a grep" — does not
hold, and that surfaced during the fix pass.** An empty grep result can
mean either that there was nothing to find, or that the command didn't
run; M26 demonstrated exactly this case (the brief's command line wasn't
runnable under `zsh` at all, and its empty output could have been booked
as proof). But a `git diff` on a **mistyped path** also prints nothing and
exits 0 — the same weakness, not a lesser one. Harder would have meant
proving the path existed beforehand, or reading `git diff --stat` over the
whole range and seeing that the file does not appear there. The finding
remains correct; its justification was not.

The milestone diff overall (`git diff --stat b6fb80b..HEAD`, HEAD =

(`SessionStore.swift` +37, `LegacyJumpSecretSweep.swift` new, 126), one
App file (`SettingsView.swift` +72), four catalogs (+10 each), two test

**No EXISTING `SecretStore` conformance is touched** — the sentence "no

## Criterion 10: met by inspection, not by test

The spec originally required as evidence "**a test over the produced
text**". That test did not exist, and in this structure it couldn't
exist: the package has **one** test target, `macSCPCoreTests`, and the
report text is produced in `ManageDataSettingsSection.runReap()`, a
`private` method of a `private struct` in the App target `MacSCPApp`. The
fix pass established this and corrected the spec (`8780a0b`): criterion
10's evidence column has since said "by inspection", not "a test over the
produced text."

**The substance of the criterion is nonetheless met**, established by
reading `Sources/MacSCPApp/SettingsView.swift`:

- Success text: `L10n.string("manageData.reapSecrets.result", "Cleanup finished.")`,
  a constant. `result.removed` is turned into a string at **no** point —
  the only formatting is
  `String(format: …"resultFailures %lld"…, result.failed)`, and `failed`
  counts observed events.
- Error text: `L10n.string("manageData.reapSecrets.failed", …)`, likewise
  constant; it names neither the cause nor the `error`.
- A UUID or a secret value cannot end up in the text, because `Result`
  carries only two `Int`s and the sweep never gets a secret's value into
  its hands at all (criterion 7).

That is an **inspection, not a test**. The difference isn't cosmetic:
whoever writes `text += " (\(result.removed))"` tomorrow breaks criterion
10, and nothing turns red. Recorded as a finding, not as a shortfall of
the implementer — the spec demanded evidence that the target structure
doesn't provide, and the task-3 report says explicitly "No new unit tests
were added for this task". **Anyone who wants to pin an assertion about
app text has to pull the text out of the view first** (a `static func
report(for:)` in Core, or a testable formatting function). That is its own
small pass; it's noted below in the backlog.

## What the milestone learned about process

Four things, each with evidence in place of assertion.

### 1. The plan's example code was wrong, and the mandated tests couldn't see it

`sessions.json` has two shapes: the container object
(`{"groups":[…],"sessions":[…]}`), since groups have existed — i.e. since
before 1.0 —, and the older bare array before that. `migrateFromLegacy()`
decodes both. The plan wrote `legacyJumpSecretIDs()` so that it decoded
**only** the array. On every installation with groups, it would therefore
have thrown on a file that the migration itself demonstrably can read —
and the sweep would have done nothing on exactly the machines it was
built for.

**All five tests the plan mandated were nonetheless green**, because tests
and code came from the same source: the plan's fixture was likewise a bare
array. A test that shares the code's assumption doesn't check the
assumption. It was only found by the review, which held the brief against
the **rest** of the code (`migrateFromLegacy`), not against itself. Fixed
in `612cb6a`, the plan updated to match in `1d1000a`; there are now two
reader tests, one per shape, plus
`legacyJumpSecretIDsThrowsWhenTheFileMatchesNeitherLegacyShape`, which
nails down that the `try?` of the first decode attempt does not swallow
the second's error.

> **The lesson:** a plan that prescribes both the test fixture *and* the
> implementation can prescribe both equally wrong. The checking authority
> has to come from outside the plan — here: the file's existing second
> reader.

### 2. A mandated test was unsatisfiable, and the implementer said so instead of bending it

The brief required `asecondRunReportsNothingRemoved`. That cannot be
produced, for two independent reasons, both of which only surfaced during
implementation:

1. `KeychainSecretStore.deletePassword` maps `errSecItemNotFound` to
   **success** (`guard status == errSecSuccess || status == errSecItemNotFound
   else { throw }`). `removed` therefore counts successful delete
   **calls**, not entries actually removed. And the legacy file stays put
   as a downgrade commitment, so the candidate set doesn't shrink — a
   second run reports the same number and changes nothing.
2. A legacy jump in **login-set mode** also carries a `secretID` (per the
   doc comment "Always present, even in set mode"), under which nothing
   was ever stored. Already the **first** run counts an empty slot here.

The only way to distinguish these would be by reading (forbidden: access
dialogs, and a failing read proves nothing) or by a new protocol member
(forbidden). **Consequence: the report names no removal count.** Spec and
plan were corrected mid-run (`c42382a`), and the test is now called
`asecondRunChangesNothingAndReportsNoFailures` — it checks **both complete
Results** (`removed: 1` on the second run too) instead of only
`failed == 0`, because `InMemorySecretStore.deletePassword` never throws
and `failed == 0` would hold for any implementation.

> **The lesson:** a number you can't trust is worse than none. And: the
> right response to an unsatisfiable requirement is to report it and
> change the **spec** — not to keep reshaping the test until it goes
> green.

### 3. The spec's security argument was wrong, and self-review corrected it

The first draft required reading the claim set from the **raw files**
rather than from `all()`, and justified that with four filter traps
(blockless `.ssh` record, unknown `authKind`, `try?` paths). Worked back
through, none of these traps actually bears, because candidates are
**exclusively** jump `secretID`s from the legacy file: a blockless `.ssh`
record has no `ssh` block and therefore no `jump` at all; a hidden login
set's ID is assigned separately and cannot be a pre-M23 jump `secretID`.

What actually matters is something else, and it's serious: **if the
session file is silently treated as empty, not a single jump `secretID`
is claimed anymore** — and the sweep deletes the secrets of every live
jump connection. From this comes the rule "never the ViewModel state,
always the stores, and they're allowed to throw" (criterion 4), and the
test that holds it (criterion 3).

Corrected in `85c17ef`. **Two success criteria would have been met
vacuously in the original version** — they would have guarded against a
danger that doesn't exist, while the real one would have been left
uncovered.

> **The lesson:** a security argument that lists several dangers isn't
> strong because there are many of them. It is exactly as strong as the
> danger that can actually occur — and that has to be worked out
> individually, not tallied from the table.

### 4. The seventeenth wrong comment on this branch arose while fixing wrong comments

A fix round claimed `ConnectionViewModel.buildJumpSpec` was "the only
place" a `JumpSpec.secretID` is produced.
`SessionImportPlanner.makePlanned` is a second real producer. Corrected in
`680d24f`. The **conclusion** survived, but for a different reason than
claimed: not because there is only one producer, but because **every**
producer mints the ID independently instead of deriving it from a set or
key ID (`existingSecretID ?? UUID()`, or the fresh default).

**Addendum from this session, so the count is correct:** there are
**four** construction sites of `StoredSession.JumpSpec` in the tree, not
two. The two additional ones sit in the App layer —
`ConnectionFormView.jumpSessionSummary` and
`ContentView.resolveSelectedJumpSession` — and build a synthetic, never-
persisted `StoredSession` for resolution ("nothing else about this
synthetic session is ever read or persisted", it says there). They too
take the fresh default. **The comment in `claimedIDs()` is therefore not
wrong** — it states a universal ("every producer … mints it
independently") and names two of them as evidence, rather than claiming
"only these two." But the evidence enumeration is incomplete, and that is
exactly the shape `680d24f` arose from. Noted here for completeness; no
fix is needed because the universal holds for all four sites.

> **The lesson, one level above M26's:** "the only place" is a claim with
> a high price and little benefit. The universal ("none of them derives
> it") carries the same argument and doesn't rot when a fifth producer is
> added.

## Two observations that are not findings, but belong in the record

**1. The run does not abort when the candidate set is empty.** `run()` has
a `guard !candidates.isEmpty else { return Result(0, 0) }` before
`claimedIDs()`. If the legacy file is **gone** (the normal case on every
fresh install) and `sessions-v2.json` is unreadable at the same time, the
run reports "Cleanup finished" instead of aborting. Criterion 5, taken
literally ("every single unreadable file aborts the run"), is not met in
this configuration; **by intent it is**, because with zero candidates
nothing can by definition be deleted, and that's what it's actually about.
The four abort tests all set up the legacy file and therefore don't hit
this configuration.

**Subsequently fixed anyway** (fix pass, see addendum below): "an abort
that does nothing would be an error message with no consequence" overlooks
that the button promises the user exactly one thing — that a check was
done. A run that reports "Cleanup finished" without having opened the
file that decides the claim set says something false, even if it deletes
nothing.

**2. The two "tests that aren't tests" don't exist.** The spec's test
hints required carrying along fixtures for the blockless `.ssh` record and
for the login set with unknown `authKind` — "but with a doc comment saying
that under today's candidate rule they cannot fail." Neither appears in
`LegacyJumpSecretSweepTests.swift` (checked by full-text search for
`blockless`/`authKind`/`dropsOnLoad` in both test files).

**That is the better outcome here, not the worse one**, and the spec says
why itself: "Without that comment they would be two tests that fake
safety." The implementer avoided the pretense by simply not writing them,
and put the argument instead where it holds: in the doc comment of
`claimedIDs()`, which names both narrowings (`load()`'s `dropsOnLoad`,
`all()`'s `authKind` filter) and explains why neither is consequential for
this candidate set. **A comment at the mechanism is better than a test
that cannot fail.** Recorded here because the spec's "test hints" section
is thereby outdated, and no one should go looking later for two tests that
never existed.

## Addendum: the fix pass after the whole-branch review (2026-08-09)

The whole-branch review over `b6fb80b..cad9606`, noted above as
outstanding, delivered one important finding and six small ones. The pass
sits in eight commits on `develop` (`git log --oneline cad9606..4b07361`
counts them any time; not pushed); in full detail in
`.superpowers/sdd/2026-08-09-m27-verwaiste-jump-secrets/final-fix-report.md`.

**The important finding: the milestone's scenario was untested.** Every
sweep test wrote `sessions-v2.json` before the legacy file and thereby
never let the migration run. So the distinguishing property the entire
safety rests on was never tested: `upgraded()` carries an `.ssh` record's
jump into the new file (it stays claimed) and drops a non-SSH record's
(it becomes an orphan). Had `upgraded()` later dropped it for `.ssh` too,
the sweep would have deleted the secrets of **every live jump
connection**, and all eighteen M27 tests would have stayed green. New
test: `sweepsOnlyTheJumpTheMigrationDropsWhenItRunsOnFirstLaunch` — no
`sessions-v2.json`, an `.ssh` and a `.webdav` legacy record each with a
jump; exactly the dropped one gets deleted. Against the mutation
(`jump: nil` for `.ssh` too) it turns red, checked and reverted again.

**Criterion 5 now holds literally.** The `guard !candidates.isEmpty` before
`claimedIDs()` is removed; both reads now run unconditionally and still
**both before the first deletion**. New test
`anUnreadableSessionFileThrowsEvenWithNoCandidates`.

**Five corrections to claims** (this branch's house lesson — four points
below, of which the last bundles two wrong sentences): the commitment "no
access dialogs" is narrowed to **read** dialogs (a deletion against an
entry whose access-control list this binary doesn't hold can very well
prompt or fail); the type header now states its actual rule ("unclaimed",
not "orphaned by M23"); the doc comment of `seedMigratedSessions` claimed
something about migration in general that only holds for its own SSH
