# M30 — Wrap-up (2026-08-19)

## What was implemented

When leaving login-set mode, an empty secret field is no longer
"unchanged" — it's now a validation error. Two calls in
`ConnectionViewModel.validateForEditSave()` now derive their secret
requirement from the transition instead of from a constant — one for the
target login (`1ee8f4c`), one for the jump (`7d0dda9`).

**The central guarantee is checked, not claimed:** the M30 commits add
not a single line containing `deletePassword` to `Sources/`. The four
loss paths that the 2026-08-09 attempt failed on are thereby not
guarded, but structurally excluded. On the production side that's 22
added lines in one file, most of it justification.

Suite: **2165 tests in 193 suites green** (previously 2157).

## The finding that only implementation revealed

The spec treated target login and jump as symmetric. They aren't:

| | Field gets cleared on switch? | Effect of the rule |
|---|---|---|
| Target login | no — there is no `selectLoginMode` | only kicks in when the field is genuinely empty |
| Jump | yes, `selectJumpLoginMode` clears password and key path (M28) | always kicks in |

So a jump that leaves set mode can **never** be saved without a freshly
typed secret. Substantively consistent — M28 clears out the set's
carried-over secret, M30 then requires one of its own — but stricter
than for the target login, and not visible in the spec.

It surfaced because
`jumpLoginModeSwitchDropsASetFilledSecretInsteadOfSavingIt` crashed: the
M28 test does a `validateForEditSave()!` on a result that it had never
previously seen as `nil`. Adjusted per maintainer decision instead of
narrowing the rule — the test now types a password, and a **different**
one from the set's. That sharpens its claim: "the set's secret does not
end up in the jump slot when nothing is typed" becomes "it doesn't end
up there even when something else is typed". Its second guarantee moved
along with it, from "no slot written at all" to "the slot holds exactly
what was typed".

## Errors in the plan

Two, both surfaced during execution:

1. **An anchor comment was quoted incorrectly** — the plan wrote `--`,
   the source has `—`. The replacement failed instead of silently
   missing, because it carried a guarantee. That a plan quote doesn't
   match the source is the rule, not the exception; the guarantee was
   cheaper than reading it again.
2. **The verification grep in Task 3 was too coarse.** `git diff
   origin/develop..HEAD | grep deletePassword` would have counted
   context lines and this morning's commits too, and would have been red
   even if M30 deletes nothing. A tool whose expected result is
   "nothing" has to be able to tell its own failure apart from success —
   here, by restricting to added lines and to the M30 commits.

## What remains open

- **Damage 1:** the own slot of a session that **is** bound to a set is
  not touched. Deliberate maintainer decision.
- `applyMerge` and the jump binding still read with `try?` and delete
  anyway — same family, untouched by M30.
- The delete path of a login set stays correct and untouched: it writes
  the set's secret into the session's slot before it nulls out
  `loginSetID`. Re-measured, see the spec.
