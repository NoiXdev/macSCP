# M11i — Cycling through candidates: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Repeated Tab in the path field cycles through the candidates, Shift+Tab goes back, Esc cancels the cycling without losing the typed input.

**Architecture:** A pure App-side change to `PathBar.swift` plus a small, testable cycle function in Core. No intervention in `PathCompletion` or `navigate(to:)`.

**Tech Stack:** Swift 6 (`.swiftLanguageMode(.v5)`), SwiftUI + AppKit, Swift Testing.

**Spec:** `docs/superpowers/specs/2026-07-30-m11i-tab-cycle-design.md`

## Global Constraints

- Code and comments **English only**; display text via the catalogs.
- No existing `@State` field changes meaning — additive only.
- The cycling mode is bound to `lastCandidates`; a new Tab round resets it
  (M11g-style care against late listings).
- The M7 rule (Shift+Tab discards outside of cycling) remains valid.
- **No App test target**: the cycle computation is factored out as a pure
  function and tested; the rest goes into the smoke checklist.
- Always verify `swift build` from a CLEAN build directory (an incremental
  run hides warnings).
- Tests: Swift Testing, TDD. Baseline: **775 tests / 55 suites**.
- No release, no merge to `main`, no tag.

### Task 1: Cycle function + Tab cycling + Esc (small Core piece + App)

**Files:**
- Create: `Sources/macSCPCore/RemoteFS/CandidateCycle.swift`
- Test: `Tests/macSCPCoreTests/CandidateCycleTests.swift`
- Modify: `Sources/MacSCPApp/PathBar.swift`

**Interfaces:**
- Produces (Core): `public enum CandidateCycle` with
  `public static func next(from current: Int?, count: Int) -> Int?` and
  `public static func previous(from current: Int?, count: Int) -> Int?` —
  `nil`/`count == 0` ⇒ `nil`; `next(nil, n) == 0`; `next(n-1, n) == 0`
  (wraparound); `previous(nil, n) == n-1`; `previous(0, n) == n-1`.
- Consumes (App): the existing `handleTab()`, `lastCandidates`,
  `lastCandidatesDirectory`, `overlayContent`, `CandidatesList`,
  `PathTextField`'s `insertBacktab` branch, `cancel()`.

- [x] **Step 1: Failing tests for `CandidateCycle`** (`CandidateCycleTests`):
  forward from `nil` ⇒ 0; forward at the end ⇒ 0 (wraparound); backward
  from `nil` ⇒ last; backward from 0 ⇒ last; `count == 0` ⇒ `nil` in both
  directions; `count == 1` ⇒ always 0.

- [x] **Step 2: Prove red.** `swift test --filter CandidateCycle` → FAIL.

- [x] **Step 3: Implement `CandidateCycle`** (pure, a few lines).

- [x] **Step 4: Green.** `swift test --filter CandidateCycle` → PASS.

- [x] **Step 5: Two new `@State` in `PathBar`.**
  `cycleIndex: Int?` (nil = not in cycling mode) and
  `cycleBaseDraft: String`. Set `cycleIndex = nil` in `beginEditing()` and
  on every new Tab round (where `justCompletedWithTab = true` is set and a
  fresh listing starts) — cycling mode must never stay bound to an old
  list. Comment with the rationale (late-listing care).

- [x] **Step 6: Extend `handleTab()`.**
  When the candidate list is visible/available (`justCompletedWithTab`
  and `lastCandidates` non-empty and `lastCandidatesDraft == draft`
  OR already in cycling mode):
  - `cycleIndex = CandidateCycle.next(from: cycleIndex, count: lastCandidates.count)`;
  - on the first step (previous `cycleIndex == nil`), remember `cycleBaseDraft = draft`;
  - `draft = RemotePath.join(lastCandidatesDirectory, lastCandidates[cycleIndex!]) + "/"`;
  - `overlayContent = .candidates(lastCandidates)` with the new
    `selectedIndex` (see Step 8).
  The existing first-tab path (listing + `completedInput`) stays
  unchanged; only the "already have a list" branch gets the cycling
  instead of merely re-displaying.

- [x] **Step 7: Shift+Tab and Esc.**
  - In `PathTextField`'s `control(_:textView:doCommandBy:)`:
    `insertBacktab` calls, **as long as the list is open**, a new closure
    `onBacktab()` and returns `true` (no focus change); if the list is
    NOT open, keep `return false` as before (M7 untouched). Whether the
    list is open is known to the view — check that state via the closure
    or a passed-in flag, don't guess it inside `PathTextField` itself.
    `onBacktab` does the same thing as a Tab, only with
    `CandidateCycle.previous`.
  - Esc: the `onCancel` path (`cancel()`) gets a preliminary step — if
    `cycleIndex != nil`, then `draft = cycleBaseDraft`, `cycleIndex = nil`,
    `overlayContent = nil`, **the field stays open** (no `isEditing = false`).
    Otherwise close as before. This holds for both the AppKit path and the
    SwiftUI wiring, so there is only one rule.

- [x] **Step 8: Highlighting + scroll in `CandidatesList`.**
  `CandidatesList` gets `selectedIndex: Int?`. The entry at that index
  gets the `remoteSoft` selection surface (like the M5g table selection)
  and is scrolled into the visible area via a `ScrollViewReader`.
  `overlayContent` must carry the index along — either as an additional
  associated value in the `.candidates` case or via a separate `@State`
  set together with the overlay. Without a selection the list looks as it
  does today (the plain second-tab state before any cycling).

- [x] **Step 9: Verification.**
  `swift build` from a clean build directory (no new warnings; four
  pre-existing ones are expected), full `swift test`. `PathBar` has no
  test target — the cycle function is the automated part, the rest is
  smoke.

- [x] **Step 10: Commit.** `feat: cycle through path completion candidates with Tab`
