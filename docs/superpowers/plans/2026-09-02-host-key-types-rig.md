# Host-Key Types in the Docker Rig — Measurement and Coverage Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The gated suite proves, per host-key type, what the client does
against a server that offers ONLY that type — ed25519, ECDSA (P-256, P-384,
P-521) and RSA — instead of proving it once against a server that offers
three types at once and letting the client pick.

**Architecture:** Measurement first. Today's rig (`docker/test-server/compose.yml`)
is a stock `linuxserver/openssh-server` offering `ssh-ed25519`,
`ecdsa-sha2-nistp256` and `ssh-rsa` host keys together; the client
(NIOSSH, `SSHKeyExchangeStateMachine.bundledServerHostKeyAlgorithms`)
prefers `ssh-ed25519`, then the three ECDSA curves, and knows RSA only if
Citadel registers a custom algorithm — and a search of Citadel's sources on
2026-09-02 found no assignment to `NIOSSHPublicKey.customPublicKeyAlgorithms`
at all, so the RSA row is expected red and Task 2 measures it rather than
assumes it. So every existing TOFU test
exercises ed25519 and nothing else. The plan adds one sshd service per
host-key type, each restricted with `HostKeyAlgorithms` in its own
`sshd_config.d` directory (the image's `sshd_config` has
`Include /config/sshd/sshd_config.d/*.conf` at line 15, ahead of its own
directives, and sshd keeps the FIRST value of a non-cumulative keyword —
so the override wins; Task 1 proves that with `ssh-keyscan` before any
Swift test relies on it). Then one gated test per service pins the type
the known-hosts store records. Where a type fails today, the test records
the failure shape as the measurement — the plan does not force it green;
that is the fork's work and gets its own entry.

**Tech Stack:** Docker compose, OpenSSH sshd, Swift Testing gated by
`MACSCP_ITEST=1`, `KnownHostsStore` (records `keyType` from the accepted
key, `CitadelFileSystem.swift:272`), `ssh-keyscan`.

**Source:** the maintainer's question of 2026-09-02 ("is the rig set up so
that all common key types are tested?") and the measurement that answered
it: agent auth covers ed25519/RSA/ECDSA P-256/384/521; file keys cover
ed25519 only (the loader refuses the rest, by design, see
`2026-09-01-ssh-key-formats.md`); host-key types are not pinned per type.

## Global Constraints

- Code, comments, identifiers, test names, commit messages: **English only**.
  Conventional Commits; footer exactly `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.
- **The rig is started from the main checkout only, never from a
  worktree** (seed mounts are relative to the compose file). Only
  macSCP's own containers (`macscp-test-*`) are touched; nothing else on
  the Docker host.
- **No key material is committed.** Host keys are generated by the image
  at container start, as today. Test client keys are generated at runtime
  with `ssh-keygen`.
- **TOFU stays a hard stop** — no test may relax host-key checking to make
  a type pass; a mismatch test per type is part of the coverage, not an
  obstacle to it.
- **A red measurement is a result, not a defect to hide.** A type the
  client cannot negotiate is recorded (error shape, exact text) in the
  closeout and in the backlog; the test for it asserts the OBSERVED
  behaviour and carries a comment naming the expected one, so it turns
  red — loudly — the day the fork makes the type work.
- The existing `sshd`/`sshd2` services keep their ports and behaviour;
  nothing existing changes.
- Gated tests only (`MACSCP_ITEST=1`); the unit suite must not need Docker.

### Task 1: One sshd service per host-key type, proved with `ssh-keyscan`

**Files:**
- Modify: `docker/test-server/compose.yml`
- Create: `docker/test-server/sshd_config.d-hostkey/ed25519/99-hostkey.conf`,
  `…/ecdsa256/99-hostkey.conf`, `…/ecdsa384/99-hostkey.conf`,
  `…/ecdsa521/99-hostkey.conf`, `…/rsa/99-hostkey.conf`
- Create: `docker/test-server/README.md` (the port table below, and the
  one-line proof command)

**Interfaces:**
- Produces: five services on fixed ports, all `testuser`/`testpass`,
  seed-less (no `/data/seed` mount is needed — the tests only connect):

| service | port | HostKeyAlgorithms |
|---|---|---|
| `sshd-hostkey-ed25519` | 2231 | `ssh-ed25519` |
| `sshd-hostkey-ecdsa256` | 2232 | `ecdsa-sha2-nistp256` |
| `sshd-hostkey-ecdsa384` | 2233 | `ecdsa-sha2-nistp384` |
| `sshd-hostkey-ecdsa521` | 2234 | `ecdsa-sha2-nistp521` |
| `sshd-hostkey-rsa` | 2235 | `rsa-sha2-512,rsa-sha2-256` |

- [ ] **Step 1:** Each `99-hostkey.conf` carries the three lines of
  `99-macscp-testrig.conf` (`PerSourcePenalties no`, `MaxStartups
  100:30:200`, `AllowTcpForwarding yes`) plus its `HostKeyAlgorithms`
  line. The P-384 and P-521 services ALSO need a host key of that curve:
  the image generates `ssh_host_ecdsa_key` as P-256 only. Add
  `HostKey /config/ssh_host_keys/ssh_host_ecdsa384_key` (resp. 521) and
  generate that key at container start — read the image's init (docker
  exec into the running `macscp-test-sshd`, look at `/etc/s6-overlay` or
  `/custom-cont-init.d` support) and use the image's documented
  custom-init hook (`/custom-cont-init.d`, mounted read-only) with a
  script that runs `ssh-keygen -t ecdsa -b 384 -N "" -f …` if the file is
  absent. Do NOT check a generated key in.
- [ ] **Step 2:** Compose: five services, same image tag as `sshd`, same
  environment, each mounting its own `sshd_config.d-hostkey/<type>` at
  `/config/sshd/sshd_config.d:ro` (and the init hook where needed).
- [ ] **Step 3: Prove the override**, from the main checkout:
  `docker compose -f docker/test-server/compose.yml up -d`, then for each
  port `ssh-keyscan -p <port> 127.0.0.1 2>/dev/null | awk '{print $2}'`
  must print exactly the one type in the table (the RSA row prints
  `ssh-rsa` — keyscan reports the key type, not the signature algorithm).
  Paste the five outputs into the README as the measurement of record,
  with the date. If a port prints more than one type, the override did
  not win: stop and report BLOCKED with the output — do not proceed to
  tests that would then measure the wrong thing.
- [ ] **Step 4: Commit** — `build(rig): one sshd service per host-key type`

### Task 2: One gated TOFU test per type, pinning the recorded key type

**Files:**
- Create: `Tests/macSCPCoreTests/HostKeyTypeIntegrationTests.swift`
  (gated like `CitadelFileSystemIntegrationTests`; copy its gate and its
  `connectWithRetry` helper by reference, do not duplicate it — move the
  helper into a shared file if it is `private`)

**Interfaces:**
- Consumes: `CitadelFileSystem.connect(config:connectTimeout:knownHosts:onUnknownHostKey:)`,
  `KnownHostsStore(directory:)`, `store.find(host:port:)` → entry with
  `keyType`.

- [ ] **Step 1:** A parameterised test over the five (port, expected
  keyType) pairs: fresh `KnownHostsStore` in a temp dir, connect with
  `.asking { _ in true }`, disconnect, `#expect(store.find(...)?.keyType == expected)`
  where expected is `ssh-ed25519`, `ecdsa-sha2-nistp256`,
  `ecdsa-sha2-nistp384`, `ecdsa-sha2-nistp521`, `ssh-rsa`. Run it. Record
  the per-row outcome in the report BEFORE changing anything.
- [ ] **Step 2:** For every row that failed, capture the exact error
  (type, text) and turn that row into its own test asserting the observed
  failure, with a comment: `// Expected once the fork can negotiate <alg>: this test turns red then, and the assertion flips.`
  Keep the passing rows in the parameterised test.
- [ ] **Step 3:** A mismatch test on ONE non-ed25519 type that passed
  (prefer `ecdsa-sha2-nistp256`): seed the store with a tampered key of
  that type (mirror `tamperedKnownKeyFailsHardWithMismatch`), connect,
  expect the hard stop, expect the decider was never asked.
- [ ] **Step 4:** Run the whole gated suite once with the rig up
  (`MACSCP_ITEST=1 swift test`) — the new services must not disturb the
  existing tests (port collisions, `MaxStartups`).
- [ ] **Step 5: Commit** — `test(ssh): pin the host-key type per rig service`

## What is explicitly not in this plan

- No change to NIOSSH or the fork. A failing type is a measured result
  here and an entry there.
- No change to the loader: file keys of other types stay refused with
  their message until the key-formats work lands.
- No agent-auth changes (already covered per type).
