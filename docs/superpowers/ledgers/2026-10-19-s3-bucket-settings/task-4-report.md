## Measured on the rig, 2026-10-19 (curl --aws-sigv4, throwaway buckets, all deleted)
1. `GET ?object-lock` on a lock-enabled bucket with no default: `200 <ObjectLockConfiguration><ObjectLockEnabled>Enabled</ObjectLockEnabled></ObjectLockConfiguration>`. 2. `GET ?retention` on an object with none: `200 <Retention></Retention>` (empty element), not the AWS-style 404. I treat both as `nil`.
3. `GET ?legal-hold` on an object never held: `200 <Status>OFF</Status>`.
4. `GET ?retention` / `?legal-hold` on a bucket WITHOUT Object Lock: `400 InvalidRequest` "Bucket is missing ObjectLockConfiguration". Not `nil`: it goes through `mapErrorStatus`.
5. `GET ?legal-hold` for a missing key: `500 InternalError` (not 404) at the rig. Left as the ordinary unexpected-status mapping.
6. **A PLAIN `DELETE` (no versionId) of an object under a GOVERNANCE retention, and of one under a legal hold, in a lock-enabled bucket answers `204` with `x-amz-delete-marker: true`. Not 403.** The lock bucket is versioned, so a plain delete adds a delete marker and removes nothing. The 403 only comes from `DELETE ?versionId=<v>`: legal hold gives `AccessDenied` "Object has a legal hold and cannot be deleted. Remove the legal hold first."; GOVERNANCE gives `AccessDenied` "Object is under GOVERNANCE retention and cannot be deleted until ..."; GOVERNANCE with `x-amz-bypass-governance-retention: true` gives 204. (I did not re-measure COMPLIANCE; it is not tested on the rig, see below.)
7. Consequence, stated plainly: macSCP's own `delete(path:)` / `deleteTree` send plain deletes, so against this store they do not meet the lock refusal; the classification below is code that the version-aware half will be the first real caller of. The doc comment on `delete(bucket:key:)` says so. A user who deletes a locked file in macSCP today sees success and the file's current version becomes a delete marker, which is correct S3 behaviour but may surprise.

## Step 4: the delete path
- `delete(bucket:key:)` now reads the response itself and, on non-2xx, calls internal `refusalOfDelete(status:body:bucket:key:)`. If the body's code is `AccessDenied`, `lockFinding` asks the object: `legalHold(...)` first (`true` -> `.objectUnderLegalHold(path:)`), then `retention(...)` (non-nil with `retainUntil > Date()` -> `.objectUnderRetention(path:)`). Anything else, including a probe that itself fails, falls through to `mapErrorStatus` unchanged (so `.authenticationFailed` for a plain 403). The path is `reportedPath(bucket:key:)` built from the caller's key.
- **Deviation from the brief's wording, deliberate:** the brief says ON means legal hold, "otherwise `objectUnderRetention`". I do not return retention unless a retention whose date has not passed is actually read. Otherwise an `AccessDenied` for a key that merely lacks `s3:DeleteObject` in a lock-enabled bucket would tell the user their file is "under a retention period", the same wrong-finding defect this work removes, pointed the other way. Costs one extra read on that failure path. Pinned by `noLockInForceMeansTheOrdinaryRefusal` (no hold/no retention, expired retention, bucket without lock -> `.authenticationFailed`). Say if you want the brief's literal rule instead.
- `deleteTree`: for a per-key `AccessDenied` the same `lockFinding` is used, with the batch's key.
- Not changed: a whole-response non-2xx on `POST ?delete`, and `rename`'s delete of the source go through whichever path they already did (rename's source delete does go through `delete(bucket:key:)` and so gets the classification).

## Concerns
1. **Plain deletes do not meet the lock refusal (finding 6).** Step 4's classification is unreachable from `delete(path:)`/`deleteTree` against the rig until a version-aware delete exists, and the gated test therefore provokes the refusal with a raw versioned `DELETE`. I think this should be on the plan's radar for the second half and for the docs ("deleting a locked file adds a delete marker").
2. **`objectLockDefault`'s `nil` covers two states** (no Object Lock; lock but no default), as the brief's signature forces. The state the UI will need for "show the section only if a lock exists" is available internally (`parseObjectLockState`) but not on the protocol. Task 6 may need a third method or a changed return type.
3. **A default expressed in Years is refused (`.protocolError`), not converted**, so a bucket whose default was set in years (by another tool) cannot be read by `objectLockDefault`. The signature has only `days`. The alternative (365 per year) would silently change the bucket if written back.
4. **Days < 1 and unreadable lock documents throw `.protocolError` with an English reason, not a new `RemoteFSFinding`** (a finding costs a case and four catalogue sentences; Task 3 review asked for a finding for CORS because a user can reach it, a day count below 1 is a form-validation matter). Say if you want a finding.
5. **Shortening a GOVERNANCE retention is not supported**: no call sends `x-amz-bypass-governance-retention`, so the store refuses it and the user would see `.authenticationFailed` (the plain mapping). `noWriteSendsTheGovernanceBypass` pins that none is sent. A UI that offers "shorten" needs a decision.
6. **Ruling C's premise, for the record, not a request to change it:** my recollection is that AWS has allowed enabling Object Lock on an existing versioned bucket since late 2023, which would make "AWS refuses it" outdated for AWS itself. I did not verify this and did not act on it; the guard and the read-first refusal are right for every provider that does not, and for the rig, either way.
7. **`refusalOfDelete` is `internal` (not private)** so the gated test can hand it a refusal; same stance as `mapErrorStatus`.
8. **No user docs written** (noix-docs); presumably the plan's closeout. **BACKLOG.md rows** about the signed Content-MD5 (see the Task 3 report concern 2) should now mention that `PUT ?object-lock` has its request-level test too (`settingTheDefaultIsAPutWithASignedContentMD5OfItsBody`); I did not edit BACKLOG.
9. The unit tests for `lockFinding` use far-future/past literal dates (2999, 2001) so no test depends on the clock. `lockFinding` itself compares to `Date()`; a skewed local clock could misjudge a retention expiring within the skew.
